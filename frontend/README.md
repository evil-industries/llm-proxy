# Management frontend

A SvelteKit 2 / Svelte 5 management console built with shadcn-svelte and Tailwind CSS 4. It manages provider credentials, client API keys, routing and logging settings, and server logs. A Node server authenticates users and forwards management requests to a private Go backend.

## Develop

Use Node.js 22.12+ and npm:

```sh
cd frontend
npm ci
cp .env.example .env
```

Generate a console password hash. Enter a password of at least 12 characters when prompted; input is hidden:

```sh
node scripts/hash-password.mjs
```

Paste the resulting hash into `AUTH_PASSWORD_HASH` in `.env`, retaining the single quotes. Set `PRIVATE_MANAGEMENT_KEY` to the Go server's management key and `PRIVATE_MANAGEMENT_URL` to its private base URL. The console password is separate from both the management key and client API keys.

```sh
npm run dev
```

Open `http://localhost:5173` and sign in at `/login`. Keep `ORIGIN` equal to the address used in your browser. Plain HTTP session cookies are supported during local development; production requires HTTPS.

Deploy this frontend with the Go server from the same checkout: client API-key changes use its atomic `/v0/management/api-keys/mutate` endpoint. Older servers will reject those changes.

The Go server needs a nonempty `remote-management.secret-key`. When Node connects from a different host or container, Go also needs `remote-management.allow-remote: true`; restrict access to its management port with private networking. Browser CORS configuration is unnecessary because browser requests stay on the console's origin.

## Authentication and configuration

| Variable                      | Purpose                                                                                                          |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `AUTH_PASSWORD_HASH`          | Scrypt hash generated by `scripts/hash-password.mjs`; never use a plaintext password here.                       |
| `PRIVATE_MANAGEMENT_URL`      | Fixed, server-only Go base URL, such as `http://cli-proxy-api:8317`.                                             |
| `PRIVATE_MANAGEMENT_KEY`      | Server-only bearer key for the Go management API.                                                                |
| `ORIGIN`                      | Exact public origin, such as `https://management.example.com`; required HTTPS in production.                     |
| `BODY_SIZE_LIMIT`             | Set to `Infinity` to disable the Node request-size limit for authenticated management uploads.                   |
| `ADDRESS_HEADER`, `XFF_DEPTH` | Behind the supplied nginx proxy only, set `x-forwarded-for` and `1` so login rate limits use the client address. |
| `HOST`, `PORT`                | Node listening address and port; the container uses `0.0.0.0:3000`.                                              |
| `MANAGEMENT_NETWORK`          | Compose-only name of the existing private Docker network; defaults to `management-backend`.                      |

The browser sends the console password to `POST /api/session`. A successful login creates an opaque, eight-hour session cookie with `HttpOnly`, `SameSite=Lax`, and production `Secure` attributes. Logout revokes the session. Every `/api/management` request requires a valid session; Node attaches the backend management key itself. The browser cannot select an upstream URL or supply the backend management key.

Authenticated management requests and responses have no application payload-size cap; uploads stream to the Go backend. The supplied Node and nginx configurations also disable request-size caps. The unauthenticated login endpoint retains its small input limit and sign-in throttling.

Sessions live in one Node process and are lost on restart. Run a single instance; horizontal scaling requires a shared session store. No browser localStorage or sessionStorage is used for credentials. Keep environment files private and outside version control; Docker excludes them from the image build context.

This is a shared operator password, not a user directory or SSO system. Password hashes use salted scrypt with N=131072, r=8, p=1, following the [OWASP scrypt baseline](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt). Sign-in attempts and concurrent password verification are bounded. Password rotation requires generating a new hash and restarting the Node process, which also invalidates existing sessions.

## Production with Node

```sh
npm ci
npm run build
NODE_ENV=production HOST=127.0.0.1 PORT=3000 ADDRESS_HEADER=x-forwarded-for XFF_DEPTH=1 node --env-file=.env build
```

Before starting, set `.env` to your production values, including `ORIGIN=https://management.example.com`. The production application rejects missing or non-HTTPS `ORIGIN` values, and always issues secure session cookies; only the development server permits HTTP cookies. Alternatively, inject the variables through your process manager and run `npm start`. Production does not automatically load `.env`; Node's `--env-file` flag loads it explicitly. Deploy `build/`, `package.json`, `package-lock.json`, and production dependencies installed with `npm ci --omit=dev --ignore-scripts`. See [SvelteKit's Node deployment documentation](https://svelte.dev/docs/kit/adapter-node).

Terminate HTTPS with a reverse proxy and forward **all routes on the console hostname** to Node. [deploy/nginx.conf.example](deploy/nginx.conf.example) provides a host nginx configuration; replace the hostname and certificate paths. Keep Node bound to loopback and the Go management server private. The supplied nginx configuration overwrites `X-Forwarded-For` with the connecting client address; `ADDRESS_HEADER=x-forwarded-for XFF_DEPTH=1` lets Node use that value for login rate limits. Only configure these variables when all incoming connections pass through this trusted proxy. Compose sets them for its loopback-bound service; the general-purpose Docker image does not trust forwarded headers by default. Do not expose a separate `/v0/management` reverse-proxy route that bypasses the console's authentication.

Preserve your existing inference ingress when adding the console. Node does not forward inference requests; clients must continue connecting to Go through an inference-only reverse proxy or a private network. Keep at least one client key configured in Go's `api-keys` list: an empty list disables its API-key authentication. Client API keys remain separate from the console password and backend management key.

For host nginx, [deploy/nginx-inference.conf.example](deploy/nginx-inference.conf.example) adds an optional `api.example.com` hostname forwarding to Go on `127.0.0.1:8317`. It permits the standard `/v1`, `/v1beta`, `/openai/v1`, and `/backend-api/codex` inference routes, forwards client authorization to Go, supports streamed responses and WebSocket upgrades, and rejects management and other routes. Replace its hostname and certificate paths and keep clients pointed at that API hostname. If your existing ingress serves additional integrations or OAuth callbacks, retain their explicit routes separately; do not replace them with an unrestricted proxy to Go.

This is a server application, not a static SPA. The existing Go `/management.html` handler serves a single downloaded HTML file and cannot host this application. Do not copy the build into `MANAGEMENT_STATIC_PATH`. `vite preview` is for local inspection, not production hosting.

## Production with Docker Compose

The multi-stage [Dockerfile](Dockerfile) builds with Node 24 and runs only the Node output and production dependencies as an unprivileged user. [compose.yaml](compose.yaml) publishes the console on `127.0.0.1:3000` for a host reverse proxy. It does not launch or publish the Go backend.

1. Create a bridge network, or use an existing private backend network:

   ```sh
   docker network create management-backend
   ```

2. Attach your Go service to this network with the DNS alias `cli-proxy-api`. For a backend managed by Compose, add this network to that service and declare it as external:

   ```yaml
   services:
     cli-proxy-api:
       # Keep your existing image, config, volume settings, and inference ingress.
       networks:
         # Retain existing networks needed by your inference reverse proxy.
         - management-backend

   networks:
     management-backend:
       external: true
       name: management-backend
   ```

   Add this network to the existing service rather than replacing its inference connectivity. Keep outbound connectivity available for provider requests; do not mark the backend network `internal: true`. Configure Go to listen on its container interface, enable remote management for the private connection, and set its management key. Preserve a nonempty `api-keys` list for inference clients. Ensure every public inference ingress denies `/v0/management` and does not expose Go's port directly.

   If you use the optional host nginx inference example, publish Go on loopback only:

   ```yaml
   services:
     cli-proxy-api:
       ports:
         - '127.0.0.1:8317:8317'
   ```

   Install and verify the inference proxy before replacing a previously public port mapping with this loopback mapping. An existing container reverse proxy can instead keep connecting over its current private network; it does not need a host port. Only omit inference ingress entirely when all inference clients connect directly over a private network.

3. Create `frontend/.env` as above, using your generated password hash and backend key. Set `PRIVATE_MANAGEMENT_URL=http://cli-proxy-api:8317` and `ORIGIN=https://management.example.com`. Container loopback is the frontend itself, so do not use `127.0.0.1` for a backend in another container.

4. From `frontend/`, validate and start:

   ```sh
   docker compose config --quiet
   docker compose up --build -d
   ```

5. Install the console nginx example on the Docker host with your TLS certificates, then open the public HTTPS origin. The console hostname must forward to `127.0.0.1:3000`, including login, session, assets, and management API routes. Keep the separate inference hostname routed to Go. Verify that a client key can access `/v1/models`, an unauthenticated request there is rejected, and `/v0/management/config` is inaccessible through the inference hostname.

Keep password hashes in single quotes in `.env`; Compose otherwise interprets dollar signs during interpolation. See [Docker's environment-file syntax](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/). `docker compose config` without `--quiet` prints resolved secrets, so avoid copying its output into logs or issues.

## Quota notifications

The gateway can send quota alerts to a self-hosted [ntfy](https://ntfy.sh/) server. Notifications are disabled by default. In the console's notification settings, enter your ntfy base URL, topic, and optional access token with publish permission, then save and enable delivery. Subscribe to the same topic in your ntfy client. Use ntfy's access controls to restrict who can publish to and read the topic.

Warning and critical thresholds are percentages of remaining quota; defaults are 20% and 5%. Alerts depend on quota observations available to the gateway. The settings show delivery status, and the test button sends a real notification using the saved settings. Saving settings does not send a test. The ntfy token remains in the Go configuration and is never returned to the browser; leaving the token field unchanged preserves it, and removing it requires the explicit clear-token action.

The Go worker checks observations every 30 seconds and continues while the browser is closed. It currently recognizes numeric Codex and Claude quota windows observed during requests. It does not poll providers for new quota data: missing signals, observations older than 15 minutes, and expired quota windows cannot trigger alerts. Other providers are not covered yet.

Reset notifications and Codex banked-reset notifications default to enabled within the master notification switch, and can be disabled independently. A reset alert requires a newer observation confirming a later quota window; an elapsed timer alone does not send one. Recovery alerts also fire when a low-quota account recovers above the warning threshold plus five percentage points, including recovery before a scheduled reset. The first healthy observation establishes a baseline without sending a reset alert.

Banked resets are available reset grants, separate from monetary credits. The gateway alerts on the first explicitly reported positive count and on subsequent count increases, without redeeming any reset. Missing counts remain unknown; decreases and zero counts update the baseline silently. OpenAI's [app-server documentation](https://learn.chatgpt.com/docs/app-server#6-rate-limits-chatgpt) defines `rateLimitResetCredits.availableCount` as authoritative. The gateway accepts the corresponding snake/camel-case field in observed `codex.rate_limits` frames and its normalized `X-Codex-Rate-Limit-Reset-Credits-Available-Count` header. This is passive compatibility support: the app-server schema does not guarantee that your upstream inference transport exposes the field. Accounts whose responses omit it cannot trigger banked-reset alerts. The gateway does not connect to the Codex app server or actively query reset grants.

Alert suppression and delivery status live in memory. Restarts, configuration changes, or multiple gateway replicas can produce repeated alerts. Failed deliveries are retried from current observations with backoff, but there is no durable notification queue. A saved destination can be tested while automatic alerts remain disabled.

The Go management API exposes `GET /v0/management/notifications`, `PUT /v0/management/notifications`, and `POST /v0/management/notifications/test`, protected by the existing management authentication. General configuration JSON omits the notification settings. The YAML `notifications` section in the repository's `config.example.yaml` provides the equivalent server configuration.

## Components and stories

```sh
npm run garden        # http://127.0.0.1:3010
npm run garden:check  # require a story for every production Svelte component
```

Each production `.svelte` file has a neighboring GardenJS `.das.js` story. `.example.svelte` files are story-only fixtures, including wrappers for snippet-based shadcn components. Garden shares the application's CSS and provides phone, tablet, and desktop presets. Stories cover populated, empty, error, disabled, and long-content states where relevant. Add or update stories whenever a component changes. Interactive examples use in-memory fixtures and do not call the production backend.

Route stories omit the reserved `+` prefix (`page.das.js` and `layout.das.js`). Use `GARDEN_PORT=3012 npm run garden` if the default port is occupied. Garden is pinned to 1.6.2 to avoid the unused, vulnerable legacy `build` dependency in later releases; the `tmp` override patches its editor dependency. Both the explorer and application use Svelte 5.

Primitives and charts in `src/lib/components/ui/` follow [shadcn-svelte](https://www.shadcn-svelte.com/docs/installation/sveltekit). `components.json` preserves the registry configuration. Charts use server-provided request-history buckets; they do not fabricate historical values or consume the usage queue. Story syntax follows the [GardenJS documentation](https://gardenjs.org/docs/get-started/examples).

## Validation

```sh
npx playwright install chromium
npm run check
npm run garden:check
npm test
npm run build
npm run test:server
```

Vitest runs server and API contract tests in Node, and component/interaction tests in real Chromium with its [Playwright browser provider](https://vitest.dev/guide/browser/). Layout checks use actual element geometry at narrow and wide viewports, including long content and enlarged text. Accessibility and keyboard checks complement overflow and clipping assertions; human visual review is still useful.

`npm run test:unit` and `npm run test:browser` run suites independently. Use `npm run format` / `npm run format:check` for formatting.

## API behavior

- Credential counters use `success` / `failed` totals returned by `/auth-files`. Charts use the credential files' recent-request history returned by the backend.
- The console never reads `/usage-queue`, because that endpoint consumes queued records.
- Data refresh is explicit. Section failures remain visible and preserve previously loaded data with a stale-data notice.
- Credential and client-key deletion require in-page confirmation. The final client API key cannot be deleted from the console, preserving API authentication. Client-key changes are atomic and identify the key in the request body. Mutations await a fresh server read after success, including when another refresh is already running.
- OAuth flows, provider API-key configuration, plugin administration, and raw YAML editing remain available through existing management tools.

Frontend CI checks types, story coverage, formatting, tests, and the Node build. The built-server smoke test also verifies the real HTTP auth gate, secure session cookie, authenticated upstream relay, cross-origin write rejection, and logout revocation. The repository's required Go compile check remains `go build -o test-output ./cmd/server && rm test-output`.
